## 1. Submission and review process

Source: <https://grafana.com/developers/plugin-tools/publish-a-plugin/publish-or-update-a-plugin> (PT `publish-a-plugin/publish-or-update-a-plugin.md`), FAQs `publish-faqs.md`, <https://grafana.com/legal/plugins/>.

- Account: a Grafana Cloud account, and you must be an administrator of the Grafana Cloud organization used to publish.
- Where: Grafana Cloud, Org Settings, My Plugins, Submit New Plugin. Updates use Submit Update on the same page.
- Form fields: single or multiple OS/arch archives; URL of the packaged ZIP; source code URL (public Git repo or ZIP; a tag URL is supported and recommended over main); SHA1 of the ZIP; testing guidance; a "provisioning provided" checkbox; and questions that decide the signature level.
- Review: (1) automated validation against the guidelines (this is plugin-validator); (2) review queue; (3) manual inspection by a reviewer: code review for quality and security, plus installing it on a Grafana instance for basic use. They may ask you to help configure a test environment and reuse it for updates.
- Timeline: no estimate given. FAQ: "We're not able to give an estimate". Update reviews "may go faster". Publish date cannot be chosen; plugins publish immediately after review.
- Approval is case by case; following best practices does not guarantee approval.
- Catalog page content is extracted from the README; to change it, submit a new version.
- Angular plugins are not accepted. `@grafana/toolkit` is deprecated, submissions based on it may be rejected. Use `create-plugin`.
- Public vs private (<https://grafana.com/developers/plugin-tools/publish-a-plugin/sign-a-plugin>, PT `sign-a-plugin.md`):
  - Public: Grafana signs as Community or Commercial after review and distributes via the catalog.
  - Private: only for your own organization, signed by you immediately with `--rootUrls`. Do not submit private plugins.
- Signature classes (<https://grafana.com/legal/plugins/>, "Last updated August 2026"): Private (free, not shareable, not Grafana Cloud compatible); Community (free; dependent technologies open source and/or not for profit; "Not commercial in nature and not affiliated with any commercial endeavor"); Commercial (paid Commercial Plugin Subscription; "offered in connection with a commercial offering, commercial dependencies or offered by a for-profit business"); Grafana; Enterprise. Community prerequisites: "Technology must be available for testing" and the plugin must already be in a public Git repo.
- Classification implication for us: InterSystems is a for-profit vendor and IRIS is commercially backed, so the Community class is likely not available and a Commercial signature (subscription; contact <integrations@grafana.com>) is the probable outcome. This is my reading of the policy text. Which class is actually assigned is decided by Grafana from the form answers: UNCONFIRMED.
- Marketplace (separate, optional): from the same page, a paid-plugin path; separate review; may be proprietary; contact <plugins-marketplace@grafana.com>. Not needed for a free plugin.

## 2. Plugin ID rules and organization slug

Sources: PT `reference/plugin-json` and the schema <https://raw.githubusercontent.com/grafana/grafana/main/docs/sources/developers/plugins/plugin.schema.json>; PV `pkg/analysis/passes/org`, `pluginname`, `typesuffix`; PT `sign-a-plugin.md` troubleshooting.

- Schema pattern for `id`: `^[0-9a-z]+\-([0-9a-z]+\-)?(app|panel|datasource)$`. The schema says: "If the plugin is published on grafana.com, then the plugin `id` has to follow the naming conventions."
- So an id has exactly 2 or 3 hyphen-separated parts: `<org>-<name>-datasource` or `<org>-datasource`. Lowercase letters and digits only inside a part.
- Our current id `intersystems-iris-datasource` matches the pattern: org `intersystems`, name `iris`, type `datasource`.
- The first segment is the Grafana Cloud org slug. Evidence it is enforced:
  - PV `org` analyzer ("Organization (exists)": "Verifies the org specified in the plugin ID exists") splits the id on `-`, takes part 0 and calls `FindOrgBySlug`. If not found it reports `missing-grafanacloud-account`, severity Warning ("The plugin's ID is prefixed with a Grafana Cloud account name, but that account does not exist. Please create the account or correct the name."). A private org returns no finding.
  - PT sign-a-plugin troubleshooting: "make sure that the Access Policy token was generated by a Grafana Cloud account that matches the first part of the plugin ID." So signing fails if the token's org does not match the id prefix.
  - PV `pluginname`: `invalid-id-format` (Warning) if fewer than 3 parts, "should follow the format org-name-type (e.g., myorg-myplugin-panel)"; `human-friendly-name` (Error) if `name` equals `id`. Skipped for plugins already published.
  - PV `typesuffix`: `plugin-type-suffix` (Error) if the id does not end in the plugin type.
- Consequence of a slug mismatch: a Warning at validation, and a signing failure for the real submission. Practical conclusion: the id prefix must equal a Grafana Cloud org you administer.
- Is `intersystems` available? Live check: `GET https://grafana.com/api/orgs/intersystems` returned HTTP 404 `{"code":"NotFound","message":"Org not found"}` on 2026-10-07. This is evidence the slug is unclaimed (or private and hidden; the PV code treats private orgs as a distinct case, so a 404 here is not fully conclusive). Whether the slug can be registered and what Grafana does to protect trademarked names: UNCONFIRMED.
- Identity verification of an org: UNCONFIRMED. I found no primary-source statement that Grafana verifies that an org is who it claims. The only mechanisms documented are the id-prefix to token-org match at signing and Grafana's manual review. Squatting risk is therefore real: register `intersystems` with an InterSystems-controlled account before submitting, and ask Grafana (<integrations@grafana.com>) about trademark handling.

## 3. Signing

Source: <https://grafana.com/developers/plugin-tools/publish-a-plugin/sign-a-plugin> (PT `sign-a-plugin.md`), <https://grafana.com/docs/grafana/latest/administration/plugin-management/plugin-sign/>, PT `publish-faqs.md`.

- Create an Access Policy: Grafana Cloud, My Account, Security, Access Policies, Create access policy. Realm: your org (all-stacks). Scope: `plugins:write`. Create a token (expiry optional but recommended). Export as `GRAFANA_ACCESS_POLICY_TOKEN`.
- Public plugin: submit for review first. If approved you are granted a signature level, then `npm run sign` (which wraps `@grafana/sign-plugin`) writes `dist/MANIFEST.txt`.
- Private plugin: `npm run sign -- --rootUrls https://example.com/grafana` (comma-separated). The rootUrls "must match the `root_url` configuration" of the target Grafana. For the 11.1.0 Kubernetes instance this means the exact `root_url`.
- What is signed: `MANIFEST.txt` has a signed message (manifestVersion, signatureType, signedByOrg, plugin id, version, time, keyId, and a SHA256 checksum for every file in the plugin) plus an OpenPGP signature verified against a public key built into Grafana. Any change to a file after signing gives "Modified signature". Windows backslash paths in the manifest must be replaced with `/`.
- You do not need to sign during development or for the first review submission. Plugin signatures do not currently expire (FAQ).
- Community plugins in CI: the scaffolded `ci.yml` signs when `GRAFANA_ACCESS_POLICY_TOKEN` is set; the release workflow uses `grafana/plugin-actions/build-plugin` with `policy_token` and optional `attestation: true` (signed build provenance). For a public plugin the token only signs after Grafana has assigned the signature level.
- Unsigned plugins: Grafana does not load them by default (log: "plugin '<id>' is unsigned"). Operators must set `allow_loading_unsigned_plugins = <plugin id>` in `grafana.ini` (or the matching `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS` env var); this is not supported on Grafana Cloud and logs a warning. Signature statuses: core, signed, unsigned, invalid, modified.
- For the Kubernetes 11.1.0 instance: until the catalog signature exists, either sign privately with its `rootUrls`, or allow the unsigned id. Either route works without the catalog.

## 4. Plugin-validator checks

Source: <https://github.com/grafana/plugin-validator> README plus the `Severity:` of each `analysis.Rule` read from `pkg/analysis/passes/*` on main (2026-10-07). Run: `docker run --pull=always grafana/plugin-validator-cli [-sourceCodeUri ...] plugin.zip` or `npx -y @grafana/plugin-validator@latest`. Levels: error, warning, ok, plus "SuspectedProblem" (LLM/diff analyzers) and "Recommendation" (provenance, plugin-docs info). `-strict` makes warnings fail. Grafana enforces its own config for submissions; local config cannot weaken it.

Errors:

- archive: `empty-archive`, `more-than-one-dir`, `no-root-dir`, `dist`; `archivename`: `no-ident-root-dir` (root folder must equal plugin id).
- metadata: `missing-metadata`, `invalid-metadata`, `metadata-not-found`, `invalid-path`, `path-relative-to-metadata`, `invalid-relative-path`, `path-not-exists` (every path referenced in plugin.json, such as logos and screenshots, must exist); `invalid-grafana-dependency` (must parse as a semver range); `plugin-type-suffix`; `human-friendly-name`; nested plugin checks.
- docs: `missing-readme`, `template-readme` (README must not be the template copy); `license-not-provided`, `license-not-valid`.
- logos: `logos` (small and large required).
- screenshots: `screenshots-image-type` (unsupported format).
- backend: `backend-binary-mission` (backend true without `executable`, or no binaries found), `backend-found-but-not-declared` (executable set but backend false), `alerting-found-but-backend-false`, `backend-binary-not-linux-amd64` (a linux/amd64 binary is mandatory), `backend-debug-file-present`, `binary-executable-found`, `binary-executable-permissions` (executable bit), `no-go-manifest`/`invalid-go-manifest`/`go-manifest-issue`.
- Go SDK (`sdkusage`): `go-sdk-not-used`, `go-mod-not-found`, `go-mod-error`, `go-sdk-replaced` (no `replace` of the SDK), `go-sdk-older-than-5-months` (Error). The 2 month variant is a Warning. In code: `fiveMonths = 30 * 5` days. This means the SDK dependency must be refreshed regularly.
- build tools: `non-standard-frontend-build-tooling` (needs `.config/webpack` or `.config/rspack` config from `@grafana/create-plugin`), `non-standard-backend-build-tooling` (needs `Magefile.go` next to `go.mod`); `legacy-builder` (`@grafana/toolkit`), `legacy-platform` (Angular).
- `module.js` missing; `js-map-*` (source map missing, invalid, mismatched); `packagejson-not-found`, `packagecode-version-mismatch` (package.json version must match plugin.json); `wrong-plugin-version` (must exceed the published version).
- security: `code-rules-violation-error` (see below), `tracking-scripts`, `unsafe-svg-file`, `webrisk-flagged` (links in plugin.json), `virus-scan-failed`, `osv-scanner` critical and high vulnerabilities in dependencies, `govulncheck-scan-failed`, `checksum-invalid`, manifest errors (`undeclared-files`, `invalid-sha-sum`, `invalid-signature`, `wrong-permissions`), `relative-link` and circular dependency checks.

Warnings:

- `missing-grafanacloud-account` (org slug), `invalid-id-format`, `missing-changelog` (CHANGELOG.md), `readme-comment`, `screenshots` (none declared), `empty-description`, `empty-keywords` (discoverability), `developer-jargon` (README), `broken-link`, `depends-on-patch-releases` and `depends-on-single-release` (grafanaDependency too narrow), `go-sdk-older-than-2-months`, `source-code-not-provided`, `unsigned-plugin`, `modified-signature`, `invalid-signature`, `private-signature` (signature analyzer, expected pre-approval), `license-with-generic-text`, `react-19-issue`, `go-sec-issue-found` (gosec), `govulncheck-issue-found`, osv moderate and low, `code-rules-violation-warning`.
- Recommendation or suspected: provenance attestation, plugin-docs info, LLM review (`llm-review`), `code-diff`.

Metadata specifics (PT `reference/plugin-json`, `publishing-best-practices`): `info.logos.small` and `large` (SVG), `info.screenshots[]` (name, path), `info.links[]` (documentation, repository, license; the reference calls links "mandatory"), `info.keywords` (accurate; irrelevant keywords are flagged in review), `info.description` (two sentences max), `info.author`, `info.version`, `info.updated`. Optional sponsorship link in `links`.

README, CHANGELOG, LICENSE: README.md required and not templated; CHANGELOG.md is a Warning if missing; LICENSE must be a recognised license (our Apache-2.0 is on the accepted list from <https://grafana.com/legal/plugins/>: AGPL-3.0, Apache-2.0, BSD, GPL-3.0, LGPL-3.0, MIT).

Binaries (PT `package-a-plugin`): name `gpx_<name>_<os>_<arch>` (+ `.exe` on Windows); the plugin.json `executable` is `gpx_<name>` (the template emits `gpx_{{snakeCase pluginName}}`; the schema says Grafana looks for `<executable>_<GOOS>_<lower-case GOARCH>`). Supported: darwin amd64/arm64, linux amd64/arm/arm64, windows amd64. Mode `0755`. ZIP root folder = plugin id (`mv dist <plugin-id>; zip -r`). Validator hard-requires only linux/amd64. Build with `mage -v` (scaffold `Magefile.go` imports `github.com/grafana/grafana-plugin-sdk-go/build` and sets `Default = build.BuildAll`; CI runs `mage buildAll` and `mage test`).

Network, secrets, telemetry:

- Policy (<https://grafana.com/legal/plugins/>): "Plugins cannot collect usage or user information", including installation statistics, sending data to third parties for analytics, embedding tracking code. Credentials must go in `secureJsonData`; TLS for transmission; no hidden files; do not manipulate environment, privileges or processes.
- Semgrep `coderules` (PV `coderules/semgrep-rules.yaml`), important for a Go backend: `os.Getenv`-style environment access is an ERROR; file-system access via `os`, `fs`, `filepath` is an ERROR; `syscall` is an ERROR; `fmt.Print*` logging is an ERROR (use the SDK `log` package); console logging in TS is a WARNING; native `alert/confirm/prompt` is an ERROR; restricted `window.*` properties are an ERROR. Rules are evaluated on the source passed with `-sourceCodeUri`. Whether `os.ReadFile` of a client certificate path is flagged: it would match the rule, so load TLS material from `secureJsonData`, not the disk.
- Outbound network access to the user's configured IRIS URL is the plugin's purpose and is not itself a violation. No analyzer inspects destinations, but the LLM review and human reviewer read the code.

## 5. Version compatibility

Sources: PT `key-concepts/manage-npm-dependencies.md`, `e2e-test-a-plugin/ci.md`, PV `grafanadependency`, `restrictivedep`; npm registry; GitHub releases API.

- `grafanaDependency` is a required plugin.json field. PV parses it with Masterminds semver (`invalid-grafana-dependency` Error if it does not parse). `restrictivedep` warns on pinning a patch release or a single release. Use a range such as `>=11.1.0`. Grafana itself refuses to load a plugin whose range excludes the running version.
- Important trap: the current create-plugin datasource template (PT `packages/create-plugin/templates/datasource/src/plugin.json`) emits `"grafanaDependency": ">=13.2.0"`. A freshly scaffolded plugin would not load on production 11.1.0. Set it by hand to `>=11.1.0`.
- Current versions on 2026-10-07: Grafana stable v13.2.3 (GitHub releases, 2026-09-29), with maintenance lines 13.1.7, 13.0.10 and 12.4.12 released the same day. `@grafana/data` and `@grafana/ui` on npm latest are 13.2.3; `@grafana/*` versions track Grafana's version number (e.g. data 11.1.0 for Grafana 11.1.0). `@grafana/plugin-e2e` latest 3.14.1. `@grafana/create-plugin` 7.12.1 (source repo version). SDK latest release v0.297.0 (2026-10-07), `go 1.26.5` in its go.mod.
- Runtime sharing: Grafana loads the plugin's `module.js` with SystemJS and shares `@grafana/*` (and react, etc.) from the host; "when the plugin is installed and executed within a Grafana instance, it inherits the version of the `@grafana` packages that the Grafana application is using". The dependency must be in Grafana's import map and externalized by the plugin's webpack config (do not edit it: "not supported and will likely lead to plugin loading failure or bugs"). So a plugin built against 13.2.3 runs on 11.1.0 with the 11.1.0 copies of `@grafana/data` and `@grafana/ui`. What breaks: any component, hook, or function added after 11.1 fails at runtime ("unavailable in the Grafana runtime environment... any page loading that part of the plugin will crash"); unit tests cannot see this.
- React: `@grafana/data` 11.1.0 through 13.0.0 declare peer `react ^18`; 13.2.3 declares `react >=19`. Grafana 11.1.0 ships React 18, so a build against 13.2.x types and the React 19 ecosystem needs care (PV also has a `react-19-issue` Warning). Whether 13.2 build output (JSX runtime) loads on React 18 hosts: UNCONFIRMED; measure it.
- Safest strategy for a min-11.1 plugin: pin `@grafana/data`, `@grafana/ui`, `@grafana/runtime`, `@grafana/schema` to an 11.x release near the minimum (e.g. 11.1.x) so the TypeScript compiler rejects APIs that do not exist there, and widen later after the e2e matrix is green. This is my recommendation, derived from the sharing mechanism above.
- Go side: the SDK is a Go module compiled into the binary, so no runtime sharing problem; the compatibility surface is the plugin protocol. The SDK's own minimum Grafana version support: UNCONFIRMED. Test an SDK of the latest release against 11.1.0 in e2e.
- Testing across versions (PT `e2e-test-a-plugin/ci.md`): the `grafana/plugin-actions/e2e-version` action resolves a matrix of Grafana Enterprise images in two modes: `plugin-grafana-dependency` (default; latest patch of each minor since the `grafanaDependency` lower bound, plus the `grafana-enterprise:nightly` image, capped at 6 versions, `max-versions` input default 6, 0 for no limit) or `version-support-policy` (latest patch per minor of the current major plus the latest minor of the previous major). With `>=11.1.0` the 6-version cap will drop old versions; set `max-versions: 0` or list the matrix explicitly (UNCONFIRMED which versions the cap keeps). create-plugin 4.7.0+ includes this matrix in `ci.yml`. Tests use `@grafana/plugin-e2e` on Playwright against the docker-compose Grafana.
- The `is-compatible` action (`plugin-actions/is-compatible`) in the scaffolded workflow compares API usage against the latest `@grafana/*` packages for each PR.

## 6. Backend plugin specifics

Sources: PT `key-concepts/backend-plugins/index.md`, `how-to-guides/data-source-plugins/add-authentication-for-data-source-plugins` (grafana.com page), `add-support-for-pdc.md`, `reference/plugin-json`, SDK `backend/error_source.go`, `backend/httpclient/*`, `experimental/status/status_source.go`, `backend/diagnostics.go`.

- Required: `QueryData` (`QueryDataHandler`, `QueryData(ctx, *QueryDataRequest) (*QueryDataResponse, error)`) for a data source backend, and `CheckHealth` (`CheckHealthResult{Status, Message, JSONDetails}`; called by the UI "Save & test" and exposed through the Grafana HTTP API). The docs describe these as capabilities; that a data source must implement both is the convention from the scaffold and the "Save & test" button, not a stated rule: UNCONFIRMED as a hard requirement. Optional: `CallResource` (custom HTTP resources, good for query-editor autocomplete such as listing namespaces or tables), streaming, metrics collection (Prometheus exposition, built into the SDK).
- Instance management: use the SDK `datasource.Manage` so state is cached per data source and rebuilt when config changes; hold a pooled HTTP client in the instance.
- `ErrorSource`: `backend.ErrorSourcePlugin` or `backend.ErrorSourceDownstream`; default when unset is plugin (`DefaultErrorSource = SourcePlugin`). Helpers: `backend.DownstreamError(err)`, `backend.PluginError(err)`, `...Errorf`, `backend.ErrorSourceFromHTTPStatus(code)`. `SourceFromHTTPStatus` returns plugin for 405, 406, 412, 413, 431, 414, 417, 426, 416, 501 and downstream for every other status. The SDK `httpclient.ErrorSourceMiddleware` wraps timeouts, cancellations, connection reset/refused and DNS failures as downstream automatically. Expectation for us: IRIS 401/403/5xx, SQL syntax errors returned by IRIS, and network failures are downstream; JSON marshalling bugs, bad query model parsing and our own panics are plugin. Grafana uses this to separate SLO accounting; the docs say nothing about enforcement at review: UNCONFIRMED.
- Resource limits: `httpclient.ResponseLimitMiddleware` and `WithResponseLimit(ctx, limit)` cap downstream response bodies (also driven by the `GF_DATAPROXY_RESPONSE_LIMIT` env var). Default HTTP timeouts: `Timeout` 30s, `DialTimeout` 10s, TLS handshake 10s, idle 90s. Apply row and size caps to SQL results so a large `SELECT` cannot exhaust Grafana memory.
- secureJsonData: credentials go in `secureJsonData` (encrypted by Grafana on save, never returned to the browser; the frontend sees only `secureJsonFields` booleans and uses password inputs and reset buttons). Read them in the backend from `DataSourceInstanceSettings.DecryptedSecureJSONData`. Not in `jsonData`, panel options, or logs.
- HTTP client: build it from the SDK (`settings.HTTPClientOptions(ctx)` then `httpclient.New`) so that Basic auth, TLS, custom headers, forwarded OAuth, tracing and PDC proxying work. Setting `ForwardHTTPHeaders = true` forwards OAuth identity headers and cookies across QueryData, CallResource and CheckHealth. The docs table says to use the plugin backend (not the proxy) for "Custom authentication, non-HTTP protocols, alerting".
- SSRF: no primary-source SSRF checklist was found: UNCONFIRMED. Observable facts: the data source URL is admin-configured; Grafana has `[plugin.<id>]` and `data_source_proxy_whitelist`/allowlist settings for the built-in proxy, which do not apply to a plugin's own backend HTTP client (my inference, not tested). Mitigations to implement: validate the URL scheme and parse it once; only call fixed IRIS paths (`/api/atelier/...`, `/api/monitor/metrics`); never build the host from a query field; do not follow redirects to other hosts.
- PDC and the secure SOCKS proxy: Grafana Cloud only. The SDK `httpclient` options carry `ProxyOptions *proxy.Options`, and the SDK HTTP client provider uses the proxy config automatically when the data source has `enableSecureSocksProxy` in jsonData. Prerequisites in PT: SDK newer than v0.229.0 and Grafana newer than 10.0.0. Frontend: add `enableSecureSocksProxy?: boolean` to the options type and a toggle gated on `config.featureToggles.secureSocksDSProxyEnabled`. PT says to skip it "if your data source is not available in Grafana Cloud". An on-prem Kubernetes install does not need it, but it is cheap if we use the SDK client.
- plugin.json flags: `backend: true` and `executable: "gpx_<name>"` for the backend; `metrics: true` for time-series; `logs: true`, `annotations: true`, `alerting: true` only if implemented. `alerting` requires `backend: true` (PV Error `alerting-found-but-backend-false`). Alerting needs queries to run purely in the backend (QueryData must not depend on frontend-only transformation) and the template-variable handling must work server side; the docs list alerting, recorded queries and query caching as reasons to have a backend. Declare `alerting: true` only after an alert rule actually evaluates.
- Provisioning guidance: PT `provide-test-environment` asks for a `provisioning/datasources/*.yml` and a sample dashboard JSON plus docker-compose so that `docker compose up` shows a working dashboard. Not required, but speeds review. Grafana's alerting-specific provisioning docs were not fetched: UNCONFIRMED.
- Logging: use the SDK `backend/log` logger; `fmt.Print*` is a validator Error.
